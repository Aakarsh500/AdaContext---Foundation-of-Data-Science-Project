# AdaContext: Budget-Aware Hybrid Evidence Selection for Long-Document QA

## Abstract

Large language models can accept increasingly long inputs, but sending an entire document for every question wastes tokens, increases latency, and may dilute relevant evidence. This project develops AdaContext, a query-aware system that predicts how much context a question needs. It combines lexical and semantic retrieval, multi-stage reranking, a lightweight learned context-budget controller, and a diversity-aware token-cost objective. The system is evaluated against full-document and fixed-retrieval baselines using answer quality, gold-evidence coverage, context precision, token consumption, and latency. It also includes a controlled lost-in-the-middle experiment and an interactive Streamlit demonstration. The complete pipeline is CPU-compatible and offers deterministic offline operation.

## 1. Problem definition

The independent variable is the context-selection strategy. Dependent variables are answer quality, evidence recall, token cost, and latency. Document length, question type, answer generator, and retrieval backend are controlled or reported as grouping variables.

Research question:

> Can a learned, question-specific context budget match the answer quality of full-document prompting while using substantially fewer input tokens?

Hypotheses:

- H1: Hybrid retrieval obtains higher evidence recall than either BM25 or dense retrieval alone.
- H2: The adaptive policy uses fewer context tokens than hybrid fixed-k retrieval at comparable answer quality.
- H3: Confidence expansion reduces failures on ambiguous or multi-evidence questions.
- H4: Adaptive evidence selection is less sensitive to document length and evidence position than full-context prompting.

## 2. Data collection

The main research dataset is QASPER, containing 5,049 questions over 1,585 NLP papers. Its expert answers include supporting evidence, enabling separate measurement of retrieval and generation. Official train, validation, and test splits are downloaded as Parquet from the Hugging Face dataset repository. A bundled fictional benchmark contains four structured reports and 24 manually authored questions for software verification.

The main experiment should train the controller on QASPER train records, tune configuration on validation records, and report final results once on test records. A laptop-friendly generation subset may be sampled after stratifying by answer type and document length, while retrieval evaluation can use a larger set.

## 3. Data preprocessing

Documents are cleaned, organized into sections, and divided into overlapping chunks without breaking sentences where possible. Metadata connects every chunk to a document, section, order, and PDF page. Gold evidence spans are normalized and matched to the most similar chunk using substring containment and token F1. Retrieval embeddings and indexes are built once per corpus.

Potential data-quality problems include PDF extraction errors, bibliography tokens in scientific papers, duplicate evidence annotations, unanswerable questions, and evidence spans that cross chunk boundaries. The pipeline retains question-level outputs so these cases can be inspected.

## 4. Exploratory data analysis

The automated EDA reports:

- Documents, questions, chunks, and tokens.
- Chunks and total tokens per document.
- Chunk-size distribution.
- Difficulty and answer-type distributions.
- Required gold-evidence chunks per question.
- Gold versus non-gold relevance-score distributions.
- Retrieval-score entropy versus evidence count.
- BM25/dense agreement, top-score gaps, and section dispersion.

Interactive HTML plots and source CSV files are generated by `scripts/run_eda.py`.

## 5. Model building

The full method is specified in `METHODOLOGY.md`. In summary, BM25 and dense embeddings produce candidate rankings, reciprocal-rank fusion combines them, and a cross-encoder can refine the top candidates. A classifier maps query/retrieval features to simple, moderate, or complex budgets. A greedy MMR-style objective chooses high-relevance, low-redundancy chunks within the budget. Low-confidence queries receive an expanded budget.

This is a small supervised model, not large-model training. Logistic regression supplies interpretability, and random forest captures nonlinear interactions. Model choice uses cross-validated balanced accuracy because the budget classes may be imbalanced.

## 6. Evaluation design

Six paired strategies answer the same held-out questions: full context, BM25 fixed-k, dense fixed-k, hybrid fixed-k, score-drop elbow, and AdaContext. The fixed hybrid baseline is necessary to isolate the value of budget adaptation.

Primary metrics:

- Token-level answer F1.
- Gold-evidence recall.
- Median selected tokens.
- Mean token reduction relative to the complete document.

Secondary metrics include exact match, context precision, selected chunks, component latency, total latency, budget accuracy, and expansion frequency. Bootstrap 95% confidence intervals express sampling uncertainty. Results are also grouped by difficulty, answer type, document length, and evidence dispersion.

Decision rule:

> Prefer a method on the Pareto frontier. If two methods differ by no more than two F1 points, prefer the one with the lower median context-token count.

## 7. Demonstration findings

The bundled dataset is a functionality benchmark rather than scientific evidence. In the included stress test, adaptive retrieval behaved consistently across beginning, middle, and end positions. Mean evidence recall was 100 percent for 10- and 25-chunk contexts and 83.3 percent for 50-chunk contexts, while median selected context remained far below the full-document baseline. These values demonstrate that the instrumentation works; final research claims must use held-out QASPER outputs generated on the student's machine.

The command below creates the final result tables:

```powershell
python scripts\evaluate.py --dataset qasper --split test --max-documents 50 --limit-questions 200 --embedding-backend tfidf
```

The reportable table is written to `reports/generated/evaluation/evaluation_summary.csv`, and the complete audit trail is in `evaluation_details.csv`.

## 8. Deployment and monitoring

The Streamlit interface supports file uploads, search scope, strategy selection, evidence display, rank-score inspection, controller reasoning, baseline comparison, evaluation, and EDA. Every normal query is appended to a JSONL log containing the selected chunks, budget, scores, tokens, and latency. No uploaded file is transmitted externally unless the user explicitly selects a hosted answer endpoint.

## 9. Limitations

- The default extractive generator cannot reliably synthesize calculations or multi-hop conclusions.
- Approximate token counts are model-independent and may differ from a provider's tokenizer.
- Cross-encoder and Sentence Transformer results depend on downloaded model versions.
- Evidence matching is approximate when annotations cross chunk boundaries.
- QASPER represents scientific papers and may not generalize to legal, conversational, or code contexts.
- LLM answer metrics are imperfect; an LLM judge should not replace transparent automatic metrics.
- Full-context inputs can exceed the chosen generator's context window and are explicitly marked when capped.

## 10. Ethical and reproducibility considerations

Answers are constrained to supplied evidence and include source identifiers. The system may still retrieve misleading or incomplete evidence, so high-stakes use requires human review. API credentials are excluded from version control. Random seeds, model names, thresholds, chunk settings, and baselines are stored in `config/default.yaml`. Dataset licenses must be retained.

## 11. Conclusion

AdaContext reframes long-context prompting as a measurable allocation problem. Its contribution is not a new large language model; it is a reproducible policy that estimates question difficulty, selects evidence under a cost budget, and exposes the quality-efficiency tradeoff. The project therefore demonstrates the full FDS cycle: problem formulation, data acquisition, preprocessing, EDA, feature engineering, predictive modeling, evaluation, deployment, and monitoring.
